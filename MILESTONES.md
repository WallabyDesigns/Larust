# Milestones

Full development history for Larust, most recent first. Every milestone
listed here is implemented, covered by tests, and has been through an
independent code review pass. See [`README.md`](README.md) for current
status and quick start, and [`rust-laravel.md`](rust-laravel.md) for the
original staged-release plan - all four planned phases (through M44's
completion of the Laravel conversion tool) are done; everything since is
organic, feedback-driven expansion on that base.

| Milestone | What it added |
|---|---|
| M100 | Fixed a second, real bug in the same restart-handoff code M98 had just repaired: `spawn_replacement_and_wait_for_ready` could return a hard `Err(BrokenPipe)` - instead of its own documented `Ok(None)` contract for "this replacement isn't viable" - when a replacement crashed fast enough to have already exited (closing its own stdin) before this process finished writing the listener encoding to it. Surfaced by CI on the exact test built to prove graceful handling of this scenario, `handoff.rs`'s own "a replacement that crashes immediately is reported as not ready." The write is now wrapped: a failure there (confirmed reachable, not theoretical - this is precisely what that test's fixture exercises) logs a `tracing::warn!`, kills and reaps the already-dead child the same way every other non-viable-replacement path already does, and returns `Ok(None)` instead of propagating the I/O error to the caller. Verified on real Linux (WSL2): 0 failures of this kind across 15 repeated runs of `handoff.rs` post-fix, and a full `larust-core` suite run clean apart from the already-diagnosed, unrelated `zero_downtime_restart.rs` kernel-backlog characteristic (M96). Full workspace `cargo check`/`clippy --all-targets -- -D warnings` clean on Windows. |
| M99 | Added `xr run`, closing a real gap in the deploy/start split: `xr deploy` with no flags publishes a release but starts nothing at all, and there was previously no dedicated command to start *that already-published release* later without either invoking its binary directly (bypassing the "already running?" idle-check `xr deploy --run` gets for free) or triggering a whole rebuild-and-republish via `xr deploy --run` again just to start something already sitting there ready to go. `xr run` resolves `storage/releases/current` (erroring clearly - "run `xr deploy` first" - if nothing's been published yet, the same non-fallback resolution `xr service:install` already uses and for the identical reason: `handoff::resolve_binary_path()`'s own `current_exe()` fallback would resolve to `xr` itself, never the deployed app), checks whether the app's own port is already being served (a short, bounded TCP connect attempt - not the admin channel, since sending it a real `RESTART` as a mere "is anything alive" check would trigger an actual, unwanted handoff of an already-running process), and is a no-op, not an error, if so. Reuses `deploy.rs`'s own `start_detached` and `service.rs`'s own `published_binary` directly (both bumped from private to `pub(crate)`) rather than duplicating either. Verified with a new, real end-to-end test (`deploy_e2e.rs`, `--ignored` like its siblings): a genuine `xr deploy` publish with no flags, followed by a genuine `xr run` that starts it, followed by a second `xr run` proving the idempotent "already being served" branch, against a real spawned process. |
| M98 | Fixed a real, previously-undetected bug that broke the zero-downtime restart handoff on Linux 100% of the time: `lifecycle::handoff::spawn_replacement_and_wait_for_ready` called `Command::spawn()` (forking the replacement) *before* `listener::prepare_for_handoff()` (duplicating the listener socket and clearing its `FD_CLOEXEC` flag) - the order Windows genuinely requires (`WSADuplicateSocketW` needs the child's real PID, which only exists after spawn returns), but fatally incompatible with Unix, where `fork()` copies the parent's fd table as a point-in-time snapshot - a fd created afterward can never retroactively reach an already-forked child. Every real Linux replacement process aborted instantly with `fatal runtime error: IO Safety violation: owned file descriptor already closed`, reconstructing a listener from a fd number the OS had never actually granted it. Root-caused by running the code on genuine Linux for the first time via WSL2 (invoked directly from this Windows-hosted session with `wsl.exe`, no separate install needed) rather than the cross-compile type-checking this file had only ever gotten before, and confirmed precisely with temporary `/proc/self/fd` diagnostics showing the "inherited" fd never existed in the child's table at any point. Fixed by running `prepare_for_handoff` before `spawn()` on Unix (Windows keeps its original after-spawn order), and closing this process's own copy of the pre-spawn duplicate once spawn returns, fixing a related fd leak (one per restart attempt, forever) as the same fix made it directly visible. `tests/listener_handoff.rs` had independently reproduced the identical "spawn before prepare" mistake in its own test-local code and needed the same reordering. Also fixed, found while chasing a red herring in the same investigation: `xr service:install` used to print manual fallback instructions and still return success (`Ok(())`) when it couldn't write the systemd unit file (e.g. not running as root) - an automated deployment tool checking only the exit code could see "success" and report a service installed when nothing had actually been written; it now returns a real error in that case, with the same instructions still printed for a human to act on. Verified: the full `larust-core` suite passes cleanly and repeatably on real Linux (WSL2), both on the workspace's own Windows-mounted path and on native Linux storage (also ruling out a `/mnt/`-path filesystem-latency red herring that had briefly looked like a second, unrelated bug); full workspace `cargo check`/`clippy --all-targets -- -D warnings` clean on Windows. |
| M97 | Disproved a GitHub Copilot diagnosis of a `dev_reload_auto_enable.rs` CI failure on `ubuntu-latest` and added real diagnostics in its place. Copilot's suggestion (bump `MAX_ATTEMPTS` from 3 to 5) assumed the M92/M95 theory that this test's restart-handoff attempts were timing out under CI load - but the CI log's own timing data contradicts that: all 3 retry attempts plus their between-attempt delays finished in 1.45s total, which is impossible if even one attempt had actually waited out the real 15s `HANDOFF_READY_TIMEOUT`. Every attempt was failing *fast*, not slow - meaning the replacement process was likely crashing or exiting immediately, not merely booting sluggishly (and casting doubt on whether the original M92 "CI is slow" theory was ever actually confirmed rather than assumed). Rather than retry blindly again, `lifecycle::handoff::spawn_replacement_and_wait_for_ready` now distinguishes and logs *why* a handoff attempt failed - the replacement's stderr closing early (a crash or deliberate early exit) vs. genuinely timing out - including its last few output lines; `lifecycle::admin`'s Unix and Windows modules now also log when `resolve_binary_path()` can't resolve a binary at all, or when spawning the replacement process fails outright (a real possibility given `cargo test --workspace` runs many of `larust-core`'s own process-spawning integration tests concurrently on a resource-constrained shared runner). `dev_reload_auto_enable.rs` now captures the fixture's own stdout into a small ring buffer and includes it in the failure message, so the next occurrence (if any) will show the actual reason instead of a bare "got FAILED." Also fixed, found incidentally while re-verifying the full suite: two unrelated `dev_reload.rs` unit tests shared one process-wide `OnceLock` broadcast channel and raced under parallel test execution (reproduced directly - one test's receiver picked up the *other* test's broadcast event) - serialized with a test-only mutex guard, the same pattern this codebase already uses elsewhere for shared global test state, confirmed stable across 5 repeated runs. Full `larust-core` suite and a full workspace `cargo check --workspace --all-targets --locked` both green. |
| M96 | Hardened `zero_downtime_restart.rs` - the test proving the framework's core "zero-downtime restart" guarantee under real concurrent HTTP traffic - against a confirmed environmental flake: the traffic-generator thread now retries a single failed request once, with a short backoff, before counting it as a real failure, mirroring the tolerance any real client (a browser, a load balancer) already has for a rare transient hiccup. Confirmed this was environmental rather than a deterministic handoff bug via two independent CI failures on separate runs - one on `windows-latest`, one on `ubuntu-latest`, two entirely different OS-level socket-handoff mechanisms (`WSADuplicateSocketW`'s duplicate-handle approach vs. Unix fd-inheritance-across-fork) - each showing the identical shape: exactly one dropped request out of 5000+ successful ones under this test's own aggressive, no-keep-alive, no-retry connection-hammering client. The same failure recurring across two unrelated OS mechanisms rules out a platform-specific socket bug and points at the test's own synthetic traffic pattern hitting an occasional transient hiccup under a loaded, shared CI runner. The test still fails if a request fails *twice* in a row - that's no longer explainable as a single transient blip - and now prints a `traffic summary` line (successes / single-retries / hard failures) on every run, passing or not, so how often the underlying blip actually occurs stays visible in CI logs going forward rather than only surfacing on an outright failure. |
| M95 | `dev_reload_auto_enable.rs`'s own test is now resilient to the CI resource contention M92 diagnosed: `the_admin_channel_is_live_under_dev_reload_with_no_app_level_opt_in` retries the `RESTART` command up to 3 times (with a short delay between attempts) if the admin channel responds `FAILED` rather than `OK`, only failing once every attempt has failed. Deliberately doesn't touch `HANDOFF_READY_TIMEOUT` itself (still the real, unmodified 15s production value governing every live `xr deploy`/`xr restart` handoff) - only the test's own tolerance for a single slow attempt on a loaded shared runner. Safe by the framework's own existing design, not a bolted-on workaround: `run_until_command`'s own doc comment already guarantees a `FAILED` response leaves the original, still-healthy process ready to accept another `RESTART` attempt later - retrying is exactly the scenario that guarantee exists for. A connect failure (the admin channel not existing at all) is still never retried, since that would mean the one thing this test exists to prove - `LARUST_DEV_RELOAD` auto-enabling the channel with no app-level opt-in - is already false, and retrying can't fix that. | M93 | Fixed a real, deterministic cross-platform bug surfaced by a `windows-latest` CI failure in `crates/larust-macros/tests/view_push_stack_resource.rs`: a single `\r` of difference (`"...<body>\r\npage body</body>"` vs the expected `"...<body>\npage body</body>"`). Traced to its exact source: `push_stack_resource_seo.blade.xr` is nothing but a `@push('head')<meta name="seo">@endpush` directive followed by one trailing end-of-file newline - the view resolver's `@push`/`@endpush` handling only strips the pushed block itself, so whatever comes *after* `@endpush` - here, just that trailing newline - renders literally at the `<resource:...>` tag's own expansion site, and the test's own hardcoded expected string already encoded this as a plain `\n`. No `.gitattributes` existed in this repo at all, so a *fresh* checkout's line-ending handling depended entirely on whatever `core.autocrlf` the checking-out machine happened to have - `windows-latest`'s `actions/checkout@v4` default (`autocrlf=true`) silently converted that one trailing LF to CRLF on checkout, while every developer's own already-existing local working tree (checked out once, long before) never got touched again and stayed LF, so this had been invisible everywhere except a genuinely fresh Windows clone - exactly what CI does on every single run. Confirmed the exact mechanism directly, not just theorized: manually flipping that one file's trailing newline to CRLF locally reproduced the byte-for-byte identical failure (`\r\n` vs `\n`, same assertion, same line), restoring it made the test pass again. Fixed with a new repo-root `.gitattributes` (`* text=auto eol=lf`, plus explicit `binary` rules for `.png`/`.jpg`/`.ico`/`.sqlite`/`.redb`/etc.) - the standard, universally-recommended fix for exactly this class of cross-platform Git checkout inconsistency, requiring no changes to the view resolver's own (deliberate, already-tested) `@push`/`@endpush` semantics at all. Takes effect automatically on every future checkout, including CI's own always-fresh clones, with no repo-wide renormalization commit required (though one's available as a follow-up via `git add --renormalize .` if every already-tracked file's line endings should be reconciled immediately rather than piecemeal as each is next touched). |

| M90 | Fixed a real bug in `xr upgrade`'s freshness check: it could report "already up to date" indefinitely even when the installed binary was genuinely stale, three days out of date in the case that surfaced it. Root cause: `run()`'s "is there anything to do" check only ever compared the checkout's own `HEAD` against its upstream (`@{u}`) - never against `BUILT_COMMIT`, the currently-installed binary's own embedded commit. Once the checkout had nothing left to *pull* (having been fast-forwarded by something other than a successful `xr upgrade` - most likely an earlier run that pulled but then failed partway through `cargo install`, though a plain manual `git pull` produces the identical symptom), this command considered its job done forever after, regardless of whether a reinstall had ever actually happened. Fixed by extracting the three-way decision into a small pure function, `plan(local_head, upstream, built_commit)` (`UpToDate` only when all three match; `ReinstallOnly` when the checkout matches its upstream but not the installed binary - the exact new case; `PullAndReinstall` when the checkout is genuinely behind), unit-tested directly (3 new tests, one per branch) without needing any real git/process I/O to exercise. `docs`/module doc comment updated with the full "up to date means *both* halves match" reasoning. |

| M88 | Added `xr service:install`/`xr service:uninstall` (`crates/larust-cli/src/service.rs`), registering a deployed app as a real `systemd` unit so it survives both a crash and a full reboot. `xr deploy --run`'s `start_detached` never claimed to survive a reboot on its own - it just spawns the app once, detached, for as long as the machine's process table lives, with nothing tying it to any init system. `WorkingDirectory`/`ExecStart` point at whatever `storage/releases/current` resolves to (requiring a real, non-empty pointer file - deliberately *not* reusing `handoff::resolve_binary_path()`'s own `current_exe()` fallback, which would resolve to `xr` itself here, the wrong binary entirely), and `WantedBy=multi-user.target` (via `systemctl enable`) starts it on boot. The one genuinely load-bearing design decision: `Restart=on-failure`, not `Restart=always` - confirmed directly against `larust_core::application::serve()`'s own source that *both* the zero-downtime handoff path and the plain `STOP` path funnel into the identical `std::process::exit(0)` once draining finishes, meaning every ordinary `xr deploy`/`xr restart` is a clean, successful exit systemd must never treat as a crash to react to; `Restart=always` would have `systemd` spawn a *second*, redundant instance racing the handoff's own already-running replacement for the same port on every single routine deploy - `on-failure` only ever fires on a real crash (non-zero exit or a killing signal), leaving the existing zero-downtime mechanism completely undisturbed and requiring zero changes to `xr deploy`/`xr restart` themselves. Linux-only, checked at runtime (`xr` itself still builds and runs everywhere) with a clear error naming the limitation on any other platform - confirmed directly against this session's own Windows machine, which correctly refused with that exact message. If `/etc/systemd/system/` isn't writable (not root), prints the generated unit file plus the exact `sudo tee .../sudo systemctl enable --now` commands instead of failing silently or attempting to self-elevate. 5 new unit tests (unit-name sanitization, generated unit-file content - explicitly asserting `Restart=on-failure` is present and `Restart=always` is not - and the release-pointer resolution's both success and clear-error paths). | M87 | `xr upgrade`'s checkout location is now overridable via `LARUST_CHECKOUT_ROOT`, closing a real gap: `xr upgrade`'s `LARUST_CHECKOUT_ROOT` (`build.rs`) was a compile-time constant baked into the `xr` binary at `cargo install` time, from wherever that install happened to run - correct for the one-machine-builds-and-uses-its-own-clone case, but wrong the moment that assumption breaks (a moved checkout, an `xr` binary shared across machines, a deployment whose layout never matches the original build machine's). `checkout_root()` already validated the path and failed loudly if stale, but offered no way to *correct* it short of rebuilding `xr` itself from a still-valid checkout. | M85 | Fixed unbounded disk growth in `xr dev`'s own throwaway `dev-*` release slots - not a problem in `xr deploy`'s production releases (already correctly bounded: it recomputes its own next slot number fresh from disk on every one-shot invocation via `release_slots::next_generation`), but a real, empirically-confirmed bug in `xr dev`'s. `DevState`'s in-memory generation counter (`rebuild_and_restart`'s `guard.generation`) started from a hardcoded `0` on every fresh `xr dev` invocation, instead of reading the real highest existing slot off disk the way `xr deploy` already does. Confirmed directly against a real `demo/storage/releases/` directory: `dev-6`, `dev-31` through `dev-34`, and `dev-37` through `dev-40` all coexisted - three-ish leftover slots per past `xr dev` restart, each one permanently unreachable by any *later* session's own `prune` call, since a fresh session's low counter can never count back up to a previous session's much higher numbers. Worse than just disk bloat: `release_slots::publish`'s own "never reuses a slot" safety invariant (the entire reason a monotonic counter exists over a fixed-size rotation) only actually held *within* one session's counter, not across a restart - a fresh session's own `dev-1` could in principle have silently overwritten a still-existing `dev-1` slot a *previous*, not-yet-fully-drained session's own generation 1 was still running from. Fixed with a new `starting_generation` (`dev.rs`), which primes `DevState.generation` from `release_slots::next_generation(app_root, "dev") - 1` - the identical disk read `xr deploy` already relies on - so numbering, and therefore pruning, always continues from wherever the disk's own history actually left off, regardless of how many `xr dev` sessions came and went in between. 3 new unit tests. Existing orphaned slots weren't deleted by hand - the fix is self-healing: the next `xr dev` session starts from the real highest generation plus one, and its own first `prune` call cleans up the rest automatically. |
| M84 | Added `xr kill` and `xr list` for managing running `xr dev`/served-app instances, plus `xr kill --id <#>` to target a specific one. The *served app* half needed no new mechanism at all - `larust_core::__internal::admin`'s existing channel already reaches "whoever is currently serving this app" by address (`larust-{app_name}`), regardless of whether it was started by `xr dev`'s own handoff, `xr deploy --run`'s cold start, or a bare `cargo run`; `xr kill` just sends the exact same `STOP` command `xr dev`'s own Ctrl+C handler already sends.
