# Milestones

Full development history for Larust, most recent first. Every milestone
listed here is implemented, covered by tests, and has been through an
independent code review pass. See [`README.md`](README.md) for current
status and quick start, and [`rust-laravel.md`](rust-laravel.md) for the
original staged-release plan - all four planned phases (through M44's
completion of the Laravel conversion tool) are done; everything since is
organic, feedback-driven expansion on that base.

|---|---|
| M89 | Directly requested as a follow-up to M88: "let's maybe add in 'xr deploy --run --service' to automatically install the service as part of the deployment, making it a single line." Added a `--service` flag to `xr deploy` (`crates/larust-cli/src/deploy.rs`), the systemd-backed sibling of `--run` for the exact same "nothing is listening to hand off to yet" branch: instead of `start_detached`'s bare, unsupervised background process, it calls the same `service::install()` M88 already built and tested, so the very first deploy is already crash-and-reboot-safe with no second `xr service:install` step needed. Wins over `--run` when both are given (matching the user's own `--run --service` phrasing) - starting the app both ways at once would just race each other for the same port; same "no effect once something is already running, or on `DEPLOY_TYPE=app`" scope `--run` already has. Verified with a real, live `xr deploy --service` run against `demo` (not just unit tests): a genuine `cargo build --release`, a genuine publish to a fresh `release-2` slot, correctly routing to the systemd path over the idle-detected branch, and correctly refusing with M88's own Linux-only guard on this session's Windows machine - proving `--service` actually takes priority and reaches the right code path, not just that it parses. Full `larust-cli` suite (128 tests), clippy, and fmt all still clean. Documented in `docs/deployment-and-desktop-apps.md` (the `xr deploy`/"Surviving a crash or a reboot" sections both updated to lead with the one-line `xr deploy --service` form) and `docs/cli-reference.md`. |
| M88 | Directly reported: "I am running a test larust project remotely. I deployed it with 'xr deploy --run' and it worked well, but when the system restarted the app did not start up again. We need to make a method for allowing apps to re-start when stopped." Confirmed with the user that the target was Linux/systemd (the overwhelmingly common real-world case, and the only one built here) before implementing. Root cause: `xr deploy --run`'s `start_detached` never claimed to survive a reboot - it just spawns the app once, detached, for as long as the machine's process table lives; nothing ties it to any init system. New `xr service:install`/`xr service:uninstall` (`crates/larust-cli/src/service.rs`) register/unregister the app as a real `systemd` unit: `WorkingDirectory`/`ExecStart` point at whatever `storage/releases/current` resolves to (requiring a real, non-empty pointer file - deliberately *not* reusing `handoff::resolve_binary_path()`'s own `current_exe()` fallback, which would resolve to `xr` itself here, the wrong binary entirely), and `WantedBy=multi-user.target` (via `systemctl enable`) starts it on boot. The one genuinely load-bearing design decision: `Restart=on-failure`, not `Restart=always` - confirmed directly against `larust_core::application::serve()`'s own source that *both* the zero-downtime handoff path and the plain `STOP` path funnel into the identical `std::process::exit(0)` once draining finishes, meaning every ordinary `xr deploy`/`xr restart` is a clean, successful exit systemd must never treat as a crash to react to; `Restart=always` would have `systemd` spawn a *second*, redundant instance racing the handoff's own already-running replacement for the same port on every single routine deploy - `on-failure` only ever fires on a real crash (non-zero exit or a killing signal), leaving the existing zero-downtime mechanism completely undisturbed and requiring zero changes to `xr deploy`/`xr restart` themselves. Linux-only, checked at runtime (`xr` itself still builds and runs everywhere) with a clear error naming the limitation on any other platform - confirmed directly against this session's own Windows machine, which correctly refused with that exact message. If `/etc/systemd/system/` isn't writable (not root), prints the generated unit file plus the exact `sudo tee .../sudo systemctl enable --now` commands instead of failing silently or attempting to self-elevate. 5 new unit tests (unit-name sanitization, generated unit-file content - explicitly asserting `Restart=on-failure` is present and `Restart=always` is not - and the release-pointer resolution's both success and clear-error paths). Documented in `docs/deployment-and-desktop-apps.md` (a full "Surviving a crash or a reboot" section explaining the `on-failure`-vs-`always` reasoning in the same depth as this entry) and `docs/cli-reference.md`. |
| M87 | Directly reported: "we need a method in the .env file for the location of the larust installation locally since it varies by installation and currently it's a hand-baked in method that will change between development and deployment." Traced to a real, specific gap: `xr upgrade`'s `LARUST_CHECKOUT_ROOT` (`build.rs`) is a compile-time constant baked into the `xr` binary at `cargo install` time, from wherever that install happened to run - correct for the one-machine-builds-and-uses-its-own-clone case `upgrade.rs`'s own doc comment already describes, but wrong the moment that assumption breaks (a moved checkout, an `xr` binary shared across machines, a deployment whose layout never matches the original build machine's). `checkout_root()` already validated the path and failed loudly if stale, but offered no way to *correct* it short of rebuilding `xr` itself from a still-valid checkout. Fixed with an environment-variable override of the identical name, `LARUST_CHECKOUT_ROOT` - read from the real process environment or a `.env` file in whatever directory `xr upgrade` runs from (the same `dotenvy::from_filename(".env").ok()` + `std::env::var(...)` pattern `restart.rs`/`dev.rs`'s own `APP_NAME`/`DEPLOY_TYPE` reads already establish, for the identical "this runs outside any compiled app" reason), winning over the compile-time default whenever set - the same precedence `RUST_LOG` already has over this crate's own logging default. The pure decision logic (`resolve_checkout_root`) was split out from the actual env read specifically so it could be unit tested (3 new tests: override wins, falls back when unset, an empty override degrades the same as unset) without mutating real process environment state in a test - `cargo test` runs every test in this binary on shared threads in one process, so a test setting `LARUST_CHECKOUT_ROOT` globally would race any other test reading environment state concurrently. Verified live, not just unit-tested: ran the real `xr upgrade` with `LARUST_CHECKOUT_ROOT` pointed at a bogus path (got back the correct, override-specific error message naming `LARUST_CHECKOUT_ROOT` rather than the old generic "the checkout this xr was built from" wording) and then at the real checkout path (succeeded normally) - both against a freshly rebuilt `xr.exe`, confirmed cleanly, clippy, and fmt. `docs/cli-reference.md`'s `xr upgrade` entry documents the override. |
| M86 | Directly asked: "when things fail, is there a log method like larust uses? ... I think if we do, we ought to give logging options to the user," with a real reference (a Laravel `SizeRotatingLogger`/`LOG_CHANNEL=stack`/`LOG_MAX_SIZE`/`LOG_KEEP_FILES` setup) to compare against. A dedicated investigation confirmed the gap was real: every generated app already logged through `tracing` (`AppError`'s own 500/panic handling already calls `tracing::error!` unconditionally), but `init_logging` wrote to stdout only - no file, no rotation, no `LOG_*` config at all, verbosity controlled purely by `RUST_LOG` or an implicit `app_env`-based default. Confirmed with the user up front that the alert-on-rotation half of their reference (`LOG_ALERT_EMAIL`/`LOG_ALERT_COOLDOWN`) should be a separate follow-up, not part of this pass - mixing mail-sending into a low-level `Write` impl is its own can of worms. Added 4 new `Config` fields (`log_channel`: `stdout` (default, unchanged behavior) / `file` / `stack`; `log_level`: empty means "unset" - same convention as `mail_username` - falling back to the original hardcoded `app_env`-based default; `log_max_size`/`log_keep_files`: rotation knobs, defaulting to 10 MiB / 5 backups) plus `AppPaths::logs()` (`storage/logs`, alongside `storage/releases`'s own precedent as the first populated `storage/<subdir>`). Also closed a related, pre-existing gap this surfaced: a freshly `xr new`-scaffolded app's own generated `.gitignore` never excluded `storage/` at all (only this workspace's own broader root `.gitignore` did) - now ignores `/storage/logs` and `/storage/releases`, so a standalone scaffolded app's own git repo won't risk committing rotated log files or built release binaries the first time either gets used. New "Logging" section in `docs/the-basics/error-handling.md`, documenting the `LOG_*` `.env` knobs, rotation behavior, and pointing power users at `RUST_LOG` for anything more targeted than a single level. |
| M85 | Investigating M84's own follow-up request ("release files seem to accumulate, eg: release-1, release-2, release-3 etc. There is no limiter perhaps?") surfaced a real, empirically-confirmed bug - not in `xr deploy`'s production releases (already correctly bounded: it recomputes its own next slot number fresh from disk on every one-shot invocation via `release_slots::next_generation`, so a real `demo/storage/releases/` directory checked directly during this investigation held exactly one `release-*.exe`), but in `xr dev`'s own throwaway `dev-*` slots. `DevState`'s in-memory generation counter (`rebuild_and_restart`'s `guard.generation`) started from a hardcoded `0` on every fresh `xr dev` invocation, instead of reading the real highest existing slot off disk the way `xr deploy` already does. Confirmed directly against that same `storage/releases/` directory: `dev-6`, `dev-31` through `dev-34`, and `dev-37` through `dev-40` all coexisted - three-ish leftover slots per past `xr dev` restart, each one permanently unreachable by any *later* session's own `prune` call, since a fresh session's low counter can never count back up to a previous session's much higher numbers. Worse than just disk bloat: `release_slots::publish`'s own "never reuses a slot" safety invariant (see that module's doc comment - the entire reason a monotonic counter exists over a fixed-size rotation) only actually held *within* one session's counter, not across a restart - a fresh session's own `dev-1` could in principle have silently overwritten a still-existing `dev-1` slot a *previous*, not-yet-fully-drained session's own generation 1 was still running from. Fixed with a new `starting_generation` (`dev.rs`), which primes `DevState.generation` from `release_slots::next_generation(app_root, "dev") - 1` - the identical disk read `xr deploy` already relies on for the identical "nothing in memory carries over between process invocations" reason - so numbering, and therefore pruning, always continues from wherever the disk's own history actually left off, regardless of how many `xr dev` sessions came and went in between. 3 new unit tests (starts at 0 with a clean directory; continues from 34 when that's the real highest existing `dev-*` slot; ignores an unrelated `release-*` slot from a real deploy, confirming the two prefixes' counting namespaces stay independent even for this new starting-point logic). The existing orphaned slots on this checkout's own `demo/storage/releases/` weren't deleted by hand - the fix itself is self-healing: the next `xr dev` session now starts from generation 41 (the real highest, `dev-40`, plus one) and its own first `prune` call cleans up everything below 38 automatically, no manual intervention needed. |
| M84 | Three related `xr` process-management requests, all stemming from the same real friction: "I think larust would benefit from an 'xr kill' event for the current directory that kills any instances tied to the current project. Also, an 'xr list' to show all running 'xr' processes, with an optional 'xr kill --id <#>' to kill a specific instance." Investigation found the *served app* half needed no new mechanism at all - `larust_core::__internal::admin`'s existing channel already reaches "whoever is currently serving this app" by address (`larust-{app_name}`), regardless of whether it was started by `xr dev`'s own handoff, `xr deploy --run`'s cold start, or a bare `cargo run`; `xr kill` just sends the exact same `STOP` command `xr dev`'s own Ctrl+C handler already sends. The genuinely new gap was `xr dev`'s own long-lived supervisor process itself: it never listens on an admin channel (only ever speaks one, to whatever it's watching over), so nothing could previously discover it exists or reach it from a second `xr` invocation at all. Closed with a new `dev_registry` module (`crates/larust-cli/src/dev_registry.rs`) - one small JSON file per running `xr dev` session, keyed by PID, in a per-user directory (`%LOCALAPPDATA%\larust\dev-sessions` on Windows, `$XDG_STATE_HOME/larust/dev-sessions` or `~/.local/state/larust/dev-sessions` on Unix), written once `xr dev` has bound its placeholder port and best-effort removed on a clean Ctrl+C exit. A crashed/force-killed session's stale file self-heals: every read (`list_live`/`find_by_pid`/`find_by_dir`) verifies the PID is genuinely still alive (`tasklist`/`kill -0`) before returning it, deleting the entry on the way past if not. `xr list` prints every live session (PID/app name/port/uptime/directory) - deliberately using the PID itself as the displayed `ID` column rather than a synthetic counter, since an ordinal would need to stay stable between one `xr list` call and a later `xr kill --id` call for the same session, which nothing can guarantee if another session exits in between; a PID already is that stable identity for as long as it's running. `xr kill` (no args) resolves the current directory's own `APP_NAME` exactly like `restart.rs` does, sends `STOP` to its admin channel, and looks up (and forcibly terminates) a registered `xr dev` session matching this directory via `dev_registry::find_by_dir`; `xr kill --id <pid>` does the same by PID instead, reachable from any directory. Termination is forceful (`taskkill /PID {pid} /F` / `kill -TERM {pid}`), not graceful, by necessity rather than oversight - `admin::STOP_COMMAND`'s own doc comment already establishes why a *targeted* graceful OS signal isn't available on Windows (`GenerateConsoleCtrlEvent` can't address one specific process), and the supervisor has no admin channel of its own to ask nicely over regardless. 8 new unit tests across `dev_registry.rs`/`list.rs`, plus a live, real end-to-end smoke test run during this session (not just unit tests): started a genuine `xr dev` against `demo`, confirmed `xr list` showed it with the correct PID/app name/port, ran `xr kill --id <pid>`, confirmed the OS process was actually gone (`Get-Process` returned nothing) and `xr list` went back to empty - then repeated the same proof for the no-args, current-directory form of `xr kill`. |
| M83 | Directly reported: "when a xr app is built using xr dev or xr build --run, the process name should reflect the app name of the project so that there are clear app separations if multiple are running and one needs to be cut off" (`xr build` itself has no `--run` flag - the actual always-backgrounded-app case is `xr deploy --run`'s cold start). Investigation found the *served app binary* was never actually the problem: Cargo already names it after the app's own `[package] name` (`demo.exe`, not something generic), and both `xr dev`'s zero-downtime handoff and `xr deploy --run`'s `start_detached` spawn that binary directly (`Command::new(binary_path)`, no wrapping shell) - so `tasklist`/Task Manager/`ps` already show a distinguishable name for the thing actually serving requests. The real, addressable gap was `xr dev`'s own long-lived supervisor process: every single running `xr dev` session shows up as an identical, indistinguishable `xr.exe`/`xr`, with no way to tell which one belongs to which project short of cross-referencing PIDs against working directories by hand - exactly the wrong moment for that, since the usual reason to look is "one of these needs to be killed right now." Fixed with a new `terminal_title` module (`crates/larust-cli/src/terminal_title.rs`), called once in `xr dev`'s `run()` right after it resolves the app's own `APP_NAME` (already read from `.env` for the admin-channel address, per `dev_config()`): the `proctitle` crate relabels the process itself (`SetConsoleTitleW` plus a named event handle discoverable in Process Explorer/Process Hacker on Windows - the same technique PostgreSQL uses; `prctl(PR_SET_NAME)`/a real `setproctitle()` call on Linux/BSD, what `ps`/`top`/`pgrep -f` report), and a raw OSC-0 escape sequence covers the terminal tab/window title on every non-Windows terminal (`proctitle` has no equivalent there itself). A user can now find and end the right one directly - `Get-Process xr | Where-Object MainWindowTitle -like "*myapp*" | Stop-Process` on Windows, `pkill -f "xr dev (myapp)"` on Linux - without matching PIDs to directories by hand. Live visual verification of the console title wasn't possible from this session's own sandboxed, non-interactive shell (no real Win32 window station to attach a console to - confirmed empirically, not assumed: `Get-Process`'s own `MainWindowHandle` came back `0` for a directly-launched `xr dev`, even outside the original git-bash/MinTTY session that has no real console at all), so correctness rests on `proctitle`'s own upstream test suite (which does assert the identical `SetConsoleTitleW`/`GetConsoleTitleW` round trip) plus this crate's full existing test suite passing unchanged (110 tests, clippy and fmt clean) - the new code adds no testable pure logic of its own, just OS calls a unit test can't meaningfully mock. |
