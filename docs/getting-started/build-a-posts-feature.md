# Build a Posts Feature
{: .no_toc }

This guided example follows one complete feature from URL to persisted data.
It uses the working blog generated by `xr new --auth`, so you can read the
source beside a running app rather than assemble unrelated snippets.

1. TOC
{:toc}

## Start with a running example

```bash
xr new examples/posts-guide --auth
cd examples/posts-guide
cargo run -- migrate
xr dev
```

Open `http://127.0.0.1:34187`, register an account, and create a post. The
starter is deliberately small, but the feature has the same layers a larger
app uses:

| Responsibility | Larust location | Laravel analogue |
|---|---|---|
| Public URLs and access rules | `routes/web.rs` | `routes/web.php` + route middleware |
| Typed input contract | `app/Http/Requests/store_post_request.rs` | Form Request |
| Persisted data | `app/Models/post.rs` + `database/migrations/` | Eloquent model + migration |
| Orchestration | `app/Http/Controllers/post_controller.rs` | Controller action |
| HTML | `resources/views/posts/*.blade.xr` | Blade view |

The names transfer on purpose. The difference is that routes, fields, and
handlers are direct Rust references the compiler can verify.

## 1. Define the boundary in the router

Readers may view posts. Creating one requires an authenticated session, so
write the public routes first and put write routes in a middleware group:

```rust
use larust_http::{Route, Router};
use larust_http::axum::middleware::from_fn;
use larust_support::auth::require_auth;

pub fn routes() -> Router {
    Route::get("/posts", PostController::index).name("posts.index")
        .get("/posts/{post}", PostController::show).name("posts.show")
        .group("", |r| {
            r.middleware(from_fn(require_auth))
                .get("/posts/create", PostController::create).name("posts.create")
                .post("/posts", PostController::store).name("posts.store")
        })
}
```

| Laravel | Larust | Why it matters |
|---|---|---|
| `Route::middleware('auth')->group(...)` | `.group("", \|r\| r.middleware(from_fn(require_auth))...)` | Larust passes the middleware function directly, so there is no string alias registry to maintain. |
| `{post}` implicit binding | `post: Post` handler argument | A missing record becomes a 404 before the handler runs. |
| Route name | `.name("posts.show")` | Link helpers can refer to a stable name instead of duplicating paths. |

Use a group when a subset shares a concern. Use top-level middleware only
when every route should inherit it. [Routing](../../the-basics/routing)
explains prefixes, nested groups, and when to use `.merge()` instead.

## 2. Make invalid input impossible to reach the action

A Form Request is both the validation declaration and the typed input your
controller receives:

```rust
use larust_support::FormRequest;

#[derive(FormRequest)]
pub struct StorePostRequest {
    #[validate(required, length(max = 255))]
    pub title: String,

    #[validate(required, length(max = 50_000))]
    pub content: String,
}
```

```rust
pub async fn store(request: StorePostRequest) -> Result<impl IntoResponse, AppError> {
    let input = request.validated();
    // Execution reaches this line only after the request was validated.
}
```

| Laravel rule | Larust rule | Result |
|---|---|---|
| `'title' => 'required|max:255'` | `#[validate(required, length(max = 255))]` | The rule is declared with the field. |
| `$request->validated()` | `request.validated()` | Both mark the safe boundary clearly. |
| Validation exception | `422` extractor rejection | The controller action is not called for invalid input. |

Form Requests currently read HTML form and multipart bodies. For JSON APIs,
use Axum's `Json<T>` extractor and apply validation suitable for that API.
The [Form Requests reference](../../the-basics/controllers-and-requests#form-requests-deriveformrequest)
lists every supported rule and current limitation.

## 3. Keep the model and schema together

The generated post model maps real Rust fields to the database table:

```rust
use larust_support::orm::sqlx;
use larust_support::Model;

#[derive(Model, sqlx::FromRow)]
#[table("posts")]
pub struct Post {
    #[primary_key]
    pub id: i64,
    pub user_id: i64,
    pub title: String,
    pub content: String,
}
```

The migration remains plain SQL:

```sql
CREATE TABLE posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL REFERENCES users(id),
    title TEXT NOT NULL,
    content TEXT NOT NULL
);
```

**Laravel comparison:** `#[derive(Model)]` provides Eloquent-shaped model
operations, including `create`, `find`, `update`, and `delete`. Unlike
Eloquent, fields live on the Rust struct instead of a dynamic property bag;
a misspelled field is a build error.

For a new resource, begin with:

```bash
xr make:model Task --migration
xr make:controller TaskController --resource
xr make:request StoreTaskRequest
```

Then replace the generator's intentionally minimal stubs with the fields and
behavior your app needs. Run `xr migrate` after editing the SQL. Continue to
[Models & Relationships](../../database/models-and-relationships) for
relationships and [Migrations & the Query Builder](../../database/migrations-and-query-builder)
for backend-specific setup.

## 4. Keep controller actions linear

The store action declares each dependency it needs: session state,
authentication, and validated input. It then persists and redirects:

```rust
pub async fn store(
    session: Session,
    Auth(user): Auth<User>,
    request: StorePostRequest,
) -> Result<impl IntoResponse, AppError> {
    let input = request.validated();
    let post = Post::create(NewPost {
        user_id: user.id,
        title: input.title,
        content: input.content,
    }).await?;

    Ok(larust_support::redirect()
        .route("posts.index")?
        .with(&session, "success", "Post published.")
        .await)
}
```

There is no controller base class or implicit request object. `Session`,
`Auth<User>`, `Post`, and `StorePostRequest` are extractors. If one cannot be
resolved—because the visitor is signed out, the model is absent, or validation
fails—the action does not execute.

That is the useful translation from Laravel: the responsibilities are familiar,
but the values and dependencies are explicit.

## 5. Render a narrow view model

Pass only the values the template needs:

```rust
Ok(larust_support::view!("posts.show", {
    id: post.id,
    title: post.title,
    content: post.content,
}))
```

```html
@extends('layouts.app')

@section('content')
    <article>
        <h1>{{ title }}</h1>
        <div>{{ content }}</div>
    </article>
@endsection
```

Blade directive names are intentionally familiar. Expressions inside
`{{ ... }}` are Rust expressions, and `.blade.xr` templates are parsed at
build time instead of interpreted per request. [Views & Templates](../../the-basics/views-and-templates)
covers layouts, escaping, components, and reactive templates.

## 6. Verify the request boundary

Run the focused tests while developing the feature:

```bash
cargo test --test store_post_test
cargo test --workspace
```

A useful feature test exercises the behavior a user sees: create the required
user state, submit a form to `/posts`, assert the redirect, then assert that
the persisted post contains the submitted data. This protects the route,
authentication, validation, controller, and database contract together.

The [Testing guide](../../testing) shows the project's `TestClient` helpers
and database-isolation patterns. Test the unhappy path too: an anonymous write
should redirect or reject, and an invalid title should return a 422 without
creating a row.

## Reuse this sequence

Every conventional Larust feature can begin with the same checklist:

1. Add the route and its access boundary.
2. Declare validated input.
3. Change the model and migration together.
4. Keep the action explicit: extract, authorize, persist, respond.
5. Render only the data the template needs.
6. Test the public request contract.

For a richer implementation of this feature, explore the repository's
[`demo/`](https://github.com/WallabyDesigns/Larust/tree/main/demo) app. It
extends the same foundation with policies, tags, comments, events,
notifications, and reactive components.
